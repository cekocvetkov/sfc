> You can also check my article [Keycloak with Quarkus and Next.js/Auth.js: Full-Stack Authentication](/article/keycloak-quarkus-next.js), which explains the same stack, but using **Keycloak** instead of **Clerk** as an authentication provider and identity management.

We’ll examine the process closely by building an application and securing it with Clerk—an authentication and user management system that handles user login, registration, and token-based security. We’ll focus on something very practical here — Clerk is widely adopted and people love using it for their SaaS products. It integrates seamlessly with **Next.js**, which is what we’re going to use for our frontend, and it’s extremely easy to set up (I mean, extremely easy).

So, like I already mentioned, we’ll use [**_Next.js_**](https://nextjs.org/) for our frontend and for the backend, we’ll use [**_Quarkus_**](https://quarkus.io/). Next.js is particularly interesting when it comes to authentication, because it can mix server-side rendering (SSR) and client-side interactions, which can create some challenges when getting the user session data. Quarkus has become my go-to backend technology for building fast, scalable, and modern APIs. Together, they create a seamless flow: Clerk authenticates users and issues tokens, Quarkus validates those tokens and secures the API, and Next.js consumes the API while delivering a smooth sign-in user experience — ensuring your application is secure. ```properties


### 5. Get a valid JWT token from Clerk for testing purposes

To get a valid token, we can use [Clerk’s Backend API](https://clerk.com/docs/reference/backend-api) — this is the perfect way to play around a bit and really understand what’s going on.
We first need to create a session, then use its session ID to generate a JSON Web Token (JWT) for this session.

So first, we need a user ID — this we can get from the Clerk’s Users Dashboard.

Then we need to send two requests — one to create a session for our user:

```bash
curl https://api.clerk.com/v1/sessions \
  --request POST \
  --header 'Content-Type: application/json' \
  --header 'Authorization: Bearer YOUR_SECRET_TOKEN' \
  --data '{
  "user_id": "",
}'
```

and one to create a token (using the `session_id` we got from the last request):

```bash
curl 'https://api.clerk.com/v1/sessions/{session_id}/tokens' \
 - request POST \
 - header 'Content-Type: application/json' \
 - header 'Authorization: Bearer YOUR_SECRET_TOKEN' \
 - data '{
 "expires_in_seconds": null
}'
```

You must replace `YOUR_SECRET_TOKEN` in the last two with your secret key, which you can find from your Clerk account under:
**Configure -> Developers/ API Keys -> Secret keys**

And that’s it — the response from the `tokens` request should contain a valid JWT token!

### 7. Role-based access

Let’s assume we want two types of users — normal ones and **admins**.

You can implement roles (like `admin` and `user` ) without paying for Clerk’s Pro/Enterprise plans or add-ons. Their free tier actually supports user metadata, which you can use for storing custom data like roles on user profiles.

Go to **Clerk’s Dashboard -> Configure -> Session Management/Sessions**

And in **Customize session token,** add this:

```json
{
 "user_metadata": "{{user.public_metadata}}"
}
```

Save. Now every JWT includes `user_metadata` (e.g., `{ "role": "admin" }`).

You can now go to **Users** in **Clerk’s Dashboard** and manually set which users you want to be admins. You can find this after you click on a user and add this to the public metadata:

```json
{
  "role": "admin"
}
```

So now we have this custom claim that we can use to see who is an admin and who is not. This means that our JWT token contains:

`{ "user_metadata": { "role": "admin" }`

To make things clean and neat in our backend, we can use the `SecurityIdentityAugmentor` from Quarkus. It can be used to customize the `SecurityIdentity`which holds the principal, roles, credentials, which were used to authenticate the client (user) and other security attributes.

We can use `@RolesAllowed` in Quarkus with Clerk’s metadata roles which we can add through the logic in our `SecurityIdentityAugmentor` . Let’s have a look at how this works.

Create a new `RoleAugmentor` class and add the following:

```java
import io.quarkus.security.identity.AuthenticationRequestContext;
import io.quarkus.security.identity.SecurityIdentity;
import io.quarkus.security.identity.SecurityIdentityAugmentor;
import io.quarkus.security.runtime.QuarkusSecurityIdentity;
import io.smallrye.mutiny.Uni;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.json.JsonString;
import org.eclipse.microprofile.jwt.JsonWebToken;

import java.util.Map;
import java.util.Optional;

@ApplicationScoped
public class RoleAugmentor implements SecurityIdentityAugmentor {

    @Override
    public Uni<SecurityIdentity> augment(SecurityIdentity identity, AuthenticationRequestContext context) {

        if (identity.isAnonymous()) {
            return Uni.createFrom().item(identity);
        }

        Optional<JsonWebToken> jwt = getJwtFromIdentity(identity);
        if(jwt.isEmpty()) {
            return Uni.createFrom().item(identity);
        }

        String role = extractRole(jwt.get());
            return context.runBlocking(()-> QuarkusSecurityIdentity.builder(identity)
                    .addRole(role)
                    .build());
    }

    private Optional<JsonWebToken> getJwtFromIdentity(SecurityIdentity securityIdentity) {
        return Optional.of(securityIdentity.getPrincipal())
                .filter(JsonWebToken.class::isInstance)
                .map(JsonWebToken.class::cast);
    }

    private String extractRole(JsonWebToken jwt) {
        Map<String, Object> metadata = jwt.getClaim("user_metadata");
        if (metadata == null || !metadata.containsKey("role")) {
            return "user";
        }

        Object roleObj = metadata.get("role");
        if (roleObj instanceof JsonString jsonString) {
            return jsonString.getString();
        } else if (roleObj instanceof String str) {
            return str;
        }

        return "user";
    }
}
```

Here we:

1. Get the JWT from the `SecurityIdentity`

2. Extract the role from our `user_metadata`

3. Build a new identity with the role that can be read from the`@RolesAllowed` annotation in our endpoint.

Now all we need to do is add this `@RolesAllowed` annotation to our endpoint:

```java
@Path("/protected")
public class ProtectedResource {
    @GET
    @RolesAllowed("admin")
    public String getProtectedResource() {
        return "SOME PROTECTED VERY IMPORTANT DATA";
    }
}
```

#### This endpoint can now only be called by admins!

```ts
import { clerkMiddleware, createRouteMatcher } from '@clerk/nextjs/server'

const isPublicRoute = createRouteMatcher(['/'])

export default clerkMiddleware(async (auth, request) => {
    if (!isPublicRoute(request)) {
        await auth.protect()
    }
})

export const config = {
    matcher: [
        // Skip Next.js internals and all static files, unless found in search params
        '/((?!_next|[^?]*\\.(?:html?|css|js(?!on)|jpe?g|webp|png|gif|svg|ttf|woff2?|ico|csv|docx?|xlsx?|zip|webmanifest)).*)',
        // Always run for API routes
        '/(api|trpc)(.*)',
    ],
}
```

#### Now it’s time to get some data from our backend!

Remember to add

```json
{
  "role": "admin"
}
```

to your user’s metadata, because we made our backend endpoint only accessible for admin users.

The next part is very easy. We just get the `jwt` token from Clerk’s convenience methods and call our backend with `Bearer <jwt>` header. We need to modify our `protected-page.tsx` yet again, to call our backend and render our response data:

```tsx
import { auth, currentUser } from "@clerk/nextjs/server"

async function ProtectedPage() {
    const user = await currentUser()
    const { getToken } = await auth()
    const token = await getToken()

    const response = await fetch("http://localhost:8080/protected", {
        headers: {
            Authorization: `Bearer ${token ?? ""}`,
        },
    })
    const responseText = await response.text()

    return (
        <div>
            <h1 className="text-2xl font-medium mb-2">Protected Page</h1>
            <p className="text-gray-600 dark:text-gray-400">Welcome ({user?.firstName} {user?.lastName})! This is a protected page.</p>
            <p className="mt-4 font-mono text-sm wrap-break-word">Response Text: {responseText}</p>
        </div>
    )
}

export default ProtectedPage
```

### Let’s recap:

- First, we created a **Clerk account**

- Then we created a **simple backend with Quarkus** with one protected endpoint. In order to connect the backend with our Clerk account, we needed just two properties — `mp.jwt.verify.issuer` and `mp.jwt.verify.publickey.location` . Our backend then uses the single`quarkus-smallrye-jwt` dependency and these two properties to verify JWT signatures and check the issuer of the JWT Tokens.

- The next part was our **Next.js frontend** — We created a sample project with one protected page (`/protected-page`). We then just needed to install the clerk dependency with `npm install @clerk/nextjs` , add our `proxy.ts` (or `middleware.ts`) file, and fill our environment variables in `.env.local` to hook up our Clerk account with our project. Next, we wrapped our whole layout with a `<ClerkProvider>` and that was it!

### Conclusion

I love how easy it is to set up Clerk. You don’t care about hosting, no servers to manage, _very_ simple SDKs (you just saw our Next.js setup), and you get a beautiful dashboard. If you compare this to using a self-hosted solution like Keycloak, you’ll see a **huge** difference (Again, you can check my article with the same stack but using **Keycloak** instead of **Clerk** [here](/article/keycloak-quarkus-next.js)). Of course, Keycloak does give you way more control and has more features out of the box, completely for free.

It’s worth mentioning that Clerk offers its more advanced features only on its **paid plan.** However, its free plan is also very (**very!**) strong and generous! It includes up to **10,000 monthly active users**, _(a user is counted as active when they return to your app 24+ hours after signing up)_ which is more than enough for most small-to-medium apps and early-stage projects. And let’s be honest — if you haven’t found a way to monetize your application when you have more than 10,000 users monthly, the cost of Clerk isn’t your real problem.
